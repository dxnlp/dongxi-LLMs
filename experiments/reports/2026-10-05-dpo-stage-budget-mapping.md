# From a fixed DPO recipe to explicit work caps

The bounded CPU reference passes: 16 new mapping controls and 19 existing
preparation controls, followed by an actual random-decoder DPO loop using the
generated cap file. The mapper connects three fixed stage recipes to the current
runner's fourteen overlapping train/evaluation/generation dimensions. It does
not authorize production, authenticate its encoding supplier or count every
operation in a process. All 45 external outcomes remain null. This reference
changes neither the learner's Day 9 progress nor the 13-of-18 bounded-package
status.

The [specification](../specs/2026-10-05-dpo-stage-budget-mapping.md) was saved
before measurement. The exclusive [run-01 verification](2026-10-05-dpo-stage-budget-mapping/run-01/verification.json)
records the actual invocation, exits, environment, 45 source hashes before and
after collection, numeric comparisons and retained refusals. Both test children
exited 0; the collector exited 0 and took 11.065 seconds. Its source hashes all
matched. This is CPU source evidence, not a Spark throughput estimate.

## What the new boundary does

[The pure mapper](../../src/dongxi_llms/dpo_stage_budget.py) imports no model or
tokenizer library and exposes no launcher. It accepts only
`assistant-dpo-smoke`, `assistant-dpo-recovery` and `assistant-dpo-pilot`.
It reconstructs the current byte-bound preparation, reads the actual local
train/validation/generation/tokenizer/template artifacts, and validates supplied
IDs, completion masks, chosen/rejected prefixes, context lengths, panel order
and cross-split identities. The observed interface and encoder-source hash must
match the preparation. Supplied geometry is bounded to 200,000 positions.

Requirements are produced before approval. A new fixture-only receipt must bind
the exact preparation, requirement hash and all fourteen cap values. Missing,
stale, coarse-only, insufficient or individually enlarged caps refuse. Extra
capacity requires a separately declared complete-attempt schedule. Real
production scope refuses; a local authored receipt cannot grant external
authority. The consumable JSON contains exactly the existing DPO reader's cap
schema, with its hash retained separately in the mapping record.

The test uses original JSONL, a saved real 16-token WordLevel backend and a saved
chat template—not the preparation fixture's earlier fictional three-token
metadata. Reloading those local artifacts and calling the actual encoder
reproduced the input order, masks, prefixes and interface exactly. That checks
this local fixture; it does not authenticate arbitrary caller-supplied records.
A future real runner must independently re-encode its pinned inputs before
using a mapping.

## Declared geometry is not actual forward work

Each update reserves chosen and rejected sequences for both policy and frozen
reference after the causal shift. Validation has separate targets and four
score branches per pair. Baseline and final uncached generation are separate
panels, each including growing-prefix positions and its complete response cap.
Overlapping dimensions are deliberate: a generation forward also consumes
policy and evaluation capacity, so the dimensions must not be summed as FLOPs.

The long-input control actually tokenized both preference branches to 512
positions. The unchanged pilot declaration has 100 updates and accumulation
four: its historical one-branch geometry is 204,800 positions. The actual shifted
training bound is 408,800 policy plus 408,800 reference positions, or 817,600
combined. Validation and two generation panels add more. This requirement is
displayed in [the unapproved pilot record](2026-10-05-dpo-stage-budget-mapping/run-01/pilot-requirements-not-authorized.json).
No pilot was fitted. A receipt retaining 204,800 as each forward cap was rejected;
neither the historical geometry nor a bare fixture receipt was silently promoted
to approval of the larger work.

## Actual CPU loop and complete schedule

The predeclared numerical recipe was seed 1818, two updates, accumulation four,
beta 0.1, AdamW learning rate 5e-7, weight decay 0.01 and gradient clipping at 1.
The random FP32 Qwen decoder has vocabulary 16, hidden width 16, intermediate
width 32, one layer, two query heads, one KV head, head dimension 8, context 512
and zero dropout. Policy gradient checkpointing is enabled; the copied reference
is frozen. It is not an acquired model or the planned pretrained SFT parent.

The host was Linux/aarch64, Python 3.12.14, Torch 2.14.1+cpu, Transformers 5.18.0,
tokenizers 0.23.2 and PEFT 0.20.0. CUDA was hidden, Hugging Face was offline and
the CPU thread budget was one. The actual DPO cap-file reader and work-contract
builder consumed the generated bytes before the baseline, training, validation
and final-generation schedule. The completed ledger's reservations exactly

## Retained failure and recovery

The separate recovery control declared capacity for two complete attempts.
It ran its baseline, completed update one, and deliberately raised an `OSError`
on entry to update two's first policy forward. Because checkpoint cadence is two,
the last durable snapshot is completed update zero, not update one. Failure
ticket 5 and all prior reservations stayed in the same physical journal.

Freshly constructed components in the **same process and CPU environment**
restored that durable update-zero snapshot and continued using the same journal.
The resumed baseline and two updates were charged again; failed work was not
refunded. Policy, reference, Adam, sampler/global Torch RNG, counters and complete
committed history matched the uninterrupted numerical endpoint exactly, with
digest `58cac828d6197548917dad9c7465e22af8dea19d3e482b44a6e1f3092be5761f`.
Resource journals, cap contracts and invocation metadata are deliberately outside
that numerical comparison. This is not a fresh-process or committed-update-one
recovery claim.

The retained journal has four update reservations but only two committed
optimizer updates at the final numerical endpoint. A requested extra whole
update then refused before `torch.randint` or model forward. The [interruption](2026-10-05-dpo-stage-budget-mapping/run-01/interruption.json),
[spending after interruption](2026-10-05-dpo-stage-budget-mapping/run-01/work-after-interruption.json)
and [spending after resume](2026-10-05-dpo-stage-budget-mapping/run-01/work-after-resume.json)
remain available. Fifteen separately retained refusal observations cover each
insufficient dimension plus the coarse-only pilot control.

The raw baseline, interrupted baseline, resumed baseline and final generations
are retained with every generated ID, stop reason, cap and error field. Baseline
and final smoke generation both failed exact match, emitted the same repetitive
sequence, reached cap 64 and were marked truncated. The held-out validation
margin is tiny, about 3.815e-6. Successful cap accounting and replay establish no
language quality, retention, generalization or preference-learning success.

## Failures preserved and scope still pending

The [first development diagnostic](2026-10-05-dpo-stage-mapping-initial-diagnostic.json)
retains three setup errors: the existing journal correctly rejected two new
fixture directories created with mode 755, and a malformed-input test attempted
to mutate an encoder tuple. The [second diagnostic](2026-10-05-dpo-stage-mapping-comparison-diagnostic.json)
retains a comparison-helper error that excluded PyTorch's `OrderedDict`.
The repairs changed directory setup and test traversal, not caps, objective,
tolerance or numerical recipe. Older preparation panels and October 4 science
remain unchanged; source-manifest additions make those panels historical rather
than current transitive-closure evidence.

These fourteen dimensions cover declared train/evaluation/generation logical
work, **not every operation in the job**. SFT/DPO recovery-history and RNG
validation overhead is still outside this mapping, as are hashing, serialization,
backward/recomputation dispatch and general CPU work. Complete-attempt allowance
is capacity, not retry permission or an enforced invocation counter. Supplier
authentication, live production source re-encoding, real parent lineage,
production artifact/export completeness, external approval, physical disk/PID/
memory containment and independent watchdog/GPU clearance remain separate gates.
The CPU fixture does not establish them. No pretrained/GPU/Mac/hosted stage,
external output or model-scale job was executed or filled.
