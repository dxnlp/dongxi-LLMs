你把一份项目方案交给 AI，问：“预算只有 50 万，这个项目做得下来吗？”

第一次，等了一会儿，回答随后流畅地出现。第二次，很快就有了开头，后面却断断续续。午后，同事们都开始使用，连开头也变慢了。

同一个模型，为什么会有三种体验？

一条回答的速度，取决于模型计算，也取决于数据怎样存放、请求怎样调度，以及计算设备之间怎样协作。 KV cache 解决了其中的重复计算问题。接下来，我们把镜头拉远，看看整套 LLM inference 系统。

这里的 inference 指运行模型获得输出；reasoning 指完成推理任务的能力与过程。本文以常见的 autoregressive Transformer 文本生成服务为主。

先花一分钟，看懂一条回答怎样产生

系统把项目文档、你的问题以及必要的消息模板组织起来，转成模型接收的 tokens。请求可能还要排队。

轮到模型处理输入时，prefill 计算 prompt 的表示，并建立 KV cache；最后一个 prompt 位置的输出用于预测第一个新 token。选出的 token 被接回序列，进入 decode，继续预测后面的 token，直到遇到停止条件。

模型给出 logits，生成策略再决定选哪个 token：greedy 选择最高分项，sampling 按处理后的概率分布抽样。生成通常使用固定权重，无需在这次回答中更新模型参数。

这就是生成的基本循环。接下来的技术都围绕它展开：少做重复工作、安排更多请求、减少存储和读取成本，或让一次验证推进更多 token。

你说的“快”，是哪一种快？

假设两次回答都输出相同数量的 tokens。一次等了 2 秒才开始，随后很流畅；另一次 0.3 秒就开始，却慢慢往外挤。数字只是说明体验差异，不是实测结果。

TTFT（Time to First Token） 关注从发出请求到收到首个输出 token 的时间。在客户端测量时，网络、排队、输入处理和 prefill 都可能占一部分。

ITL（Inter-Token Latency） 关注后续输出 token 之间的间隔。它影响回答是否流畅。平均每个输出 token 的时间也常用 TPOT 表示；看报告时，需要确认定义、是否排除首 token，以及测量位置。

还有两个不同的问题：你多久拿到完整答案，以及系统每秒总共服务了多少工作。前者是端到端延迟，后者是吞吐量，可以用 output tokens/s 或 requests/s 等口径报告。

全站每秒输出更多 token，你的这条回答仍可能等得更久。 请求长度、到达速度和并发量都会改变这些指标。对比吞吐量时，必须同时看负载和延迟要求。

还有一个容易误判的地方：reasoning 模型可能先产生未展示的中间 tokens。用户看到首个答案文字的时间，与服务记录的首 token 时间可能不同。比较性能前，先确认自己测的是哪一个时刻。

大家同时来问，GPU 怎样安排？

上午只有你一个人问预算。下午，一位同事只要一句总结，另一位要完整的风险报告，还有人不断发来新问题。

Batching 把多个请求的计算组织在一起，通常能让 GPU 更有效地执行矩阵运算。但这些请求不会同时结束。

如果一批请求的成员固定，短回答结束后，新请求仍可能要等待下一批。Continuous batching 在生成迭代之间重新安排成员：完成的请求退出，等待中的请求在资源允许时加入，长回答继续生成。

GPU 可以共同处理几个人的计算，但他们的对话不会因此混在一起。调度器还要考虑 token 预算、可用 KV 空间与公平性。让更多请求同时运行，也可能让每条请求的一步计算更重。

这时，KV cache 的存储方式也重要。PagedAttention 将逻辑上连续的 KV 序列映射到分块存储，减少大块连续预留造成的浪费，并支持灵活的分配与共享。它让不同长度的请求更容易共存；attention 仍然要读取所需的历史状态。

文档越来越长：复用、分段，还是分开处理？

现在，你的方案从几页变成了一整套资料。系统既要处理这份长输入，也要让同事正在接收的回答继续流畅输出。

这可以从三个层面处理。

Prefix caching：这段输入以前算过吗？

你先问风险，再把同一份文档放在问题前，问预算。若实际 token 前缀相同、执行条件兼容、缓存仍可用，就可以复用该前缀的 KV，跳过相应 prefill。新问题仍需计算，新答案仍需生成。

Chunked prefill：这份长输入能否分段安排？

将长 prompt 的 prefill 拆成较小的调度单元，穿插到其他请求的 decode 工作中。这样可以避免一次很大的 prefill 长时间干扰正在输出的请求。

分段后，文档的上下文关系仍然保留，后面的片段可以利用前面已经计算的状态。它不把一份方案变成几份互不相干的短文，也不自动省掉输入计算。分块大小需要权衡：照顾正在输出的用户，可能让长文档自身更晚完成 prefill。

Prefill/decode 分离：两个阶段能否分别安排资源？

让 prefill worker 处理输入，再把需要的 KV 状态交给 decode worker 继续生成。两个执行池可以采用不同的资源配比和并行设置，降低新输入处理对输出节奏的干扰。

为什么值得区分？长 prompt 的 prefill 往往能组织较大的矩阵计算；小 batch 的 decode 则常受权重、KV 的读取带宽限制。这只是常见倾向，瓶颈会随模型、上下文、batch 和硬件变化。

分离的代价是 KV 传输、额外调度和两个池之间的负载平衡。vLLM 的相关说明侧重分别调优 TTFT 与 ITL、控制尾部延迟，并明确提醒：不要把分离本身当作吞吐量提升。

把这一组记成三个问题就够了：哪些可以不重算？何时分段计算？在哪些资源上计算？

回答生成得慢：一次能否推进几个 token？

项目报告要写得很长。即使历史 KV 都在，标准 decode 仍要一轮轮运行目标模型。

Speculative decoding 先用成本较低的方式提出一段候选，再让目标模型并行计算这些候选位置所需的验证结果。候选可以来自小模型，也可以来自其他预测机制。

假设提出了四个候选 token：a、b、c、d。目标模型按规则接受了 a、b，在 c 处拒绝。系统保留已接受的前缀，在拒绝处产生修正 token；原来基于 c 提出的 d 也不能直接沿用。

这里的“验证”是按目标模型的概率规则检查候选，不能理解成事实核查。正确的 exact speculative sampling 使用接受与修正规则，在理想数值条件下保持目标采样分布；这不保证每次运行得到逐字相同的答案。

它为什么可能快？一次目标模型验证有机会接受多个 token，减少逐个运行目标模型的轮数。但验证本身仍有计算成本，提议候选也要花时间。

接受得多、提议便宜，才更有机会获得收益。 候选经常被拒绝、GPU 已经很忙，或者草稿计算成本过高时，加速会减小，甚至得不偿失。不要把“提出四个”理解成“四倍加速”。

模型太大：先分清谁占了显存

你换了一个更大的模型，或者允许更多人同时处理长文档，显存很快吃紧。

先看两笔不同的占用：权重存放模型参数，KV cache保留正在使用或等待复用的输入状态。此外还有临时 tensors、运行时缓冲区等开销。

量化（quantization） 用更低位宽的表示存放权重或其他 tensors，减少对应存储，并可能降低数据传输量。有的方案还会量化计算中的 activations。

做一个纯粹的账面计算：假设模型恰有 80 亿个参数，全部按 16 bit 存储，权重 payload 是 16 GB；全部按 4 bit 紧凑存储，则是 4 GB。这里使用十进制 GB，忽略 scales、元数据、未量化层和对齐开销，更没有算 KV cache。

权重量化不会自动缩小另一笔 KV 占用。长文档和高并发下，还可以评估 KV cache quantization，但它有独立的精度、格式和 kernel 支持要求。

量化后的回答可能变化。对项目文档场景，要检查预算数字、约束提取和长上下文表现。低位宽也不保证更快：硬件是否支持高效计算、kernel 怎样处理解量化、实际瓶颈在哪，都需要验证。

多加几张 GPU，就能线性变快吗？

先问：你想容纳更大的模型，还是服务更多人？

拆一个模型。 Tensor parallelism（TP）把某些层内 tensors 和运算分到多张 GPU；pipeline parallelism（PP）按层划分阶段，依次传递中间表示。它们可以组合，让单张 GPU 放不下的模型运行起来。

代价是通信、同步和阶段间等待。GPU 之间怎样连接很重要；两张设备的显存相加，也不等于获得一张同样容量、没有通信开销的设备。

复制多个实例。 模型能容纳在一个实例中，就可以部署多个副本，由服务系统分发不同请求。一个副本也可以由多张 GPU 共同承载。对普通 dense 模型，这是理解 inference data parallelism 的直接方式。

更多副本可以减少拥堵、承接更多用户，但一条请求通常仍由分配到的模型实例处理，其逐步生成计算不会自动按副本数量加速。

MoE 还会涉及 expert parallelism：把不同 experts 分布到设备上，并路由 token 表示。这里先保留这个位置，不展开它与其他并行方式的组合。

技术很多，先找你的那种“慢”

回到最初的项目方案。现在可以按现象提问了：

  • 长文档每次都等很久：先看输入处理、排队和 prefill 各占多少，再检查可复用前缀。
  • 别人上传长文档时，我的回答卡顿：看 prefill/decode 的调度干扰，再评估 chunked prefill 或阶段分离。
  • 开始很快，长答案生成慢：看 decode 的带宽、计算和批量条件，再评估 speculative decoding。
  • 人一多就排队：看 continuous batching、KV 容量和副本规模，不能只看单请求 tokens/s。
  • 模型放不下，或者长上下文撑满显存：分清权重与 KV 的占用，再决定量化或并行方式。

如果有人告诉你“推理快了两倍”，可以接着问：相同模型和精度吗？输入、输出有多长？缓存是冷的还是热的？同时有多少请求？提升的是 TTFT、输出速度，还是系统吞吐量？回答质量是否保持可接受？

再看延迟分布。平均值不错，一小部分请求仍可能很慢；P95 表示约 95% 的观测延迟不超过这个值。交互式服务通常也关心这些尾部等待。

真正有价值的优化，是在明确的质量、成本和等待时间要求下，让系统完成更多有用工作。
